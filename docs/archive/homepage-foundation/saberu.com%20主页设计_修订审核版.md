# saberu.com 主页设计（修订审核版）

> 版本：v1.1 · 修订日期：2026-10-11 · 状态：**推荐方案，待项目负责人批准 P1**  
> 文档性质：原《saberu.com 主页设计》的技术修订稿；仅更新本次提供的文档副本，**未修改仓库中的正式计划，也未部署**。

## 1. 目标、范围与决策摘要

为 saberu.com 建设中文、英文、日文三语品牌主页。技术栈为 Next.js App Router + next-intl，使用 Docker standalone 镜像在自有主机运行，经 Cloudflare Tunnel 对外提供服务。当前只交付一个首页，但为增加公开内容和未来交互功能留出合理扩展空间。

**推荐而非已授权的架构决策**：公开页面使用统一语言前缀 `/zh`、`/en`、`/ja`；根路径 `/` 只做语言协商与跳转；所有语言共享**同一份** React 页面和组件代码，翻译文本分别保存在 JSON 资源文件中。没有任何“每种语言复制一套页面文件”的要求。

| 项目 | 推荐做法 | 边界 |
| --- | --- | --- |
| 页面路由 | `/[locale]` | `[locale]` 是动态参数，不是三份目录 |
| 翻译 | `messages/{zh,en,ja}.json` | 统一语言列表；增加语言需补翻译并验证 |
| 语言入口 | `/` 判断偏好后临时跳转 | 不应被 CDN 缓存为所有用户共用的目标 |
| 语言选择 | 明确选择写持久化 Cookie | 访问分享的其他语言链接不得覆盖“主动选择”偏好 |
| 语言切换 | 客户端导航优先 | 不承诺所有组件不重挂载；重要状态另行保障 |
| SEO | 各语言固定 URL、canonical、hreflang、sitemap | 只提高可发现性，不保证一定收录 |
| 部署 | Docker + Cloudflare Tunnel | 上线前先验证源站，再切换流量 |

### 1.1 本期做 / 不做

**P1**：工程骨架、国际化、首页占位、单元与端到端测试、容器构建。  
**P2**：品牌文案、视觉、图标、分享图和内容检查。  
**P3**：发布、DNS/Tunnel/维护页切换、回滚验证。  
**本期不做**：登录系统、Dashboard、复杂表单编辑器、WebSocket、CMS、多语言自动翻译或混合路由。未来有真实需求时另行设计，避免过早复杂化。

## 2. URL 与页面文件：为什么选择语言前缀

### 2.1 单一页面代码与多份语言资源

```text
src/
├── app/
│   ├── [locale]/
│   │   ├── layout.tsx            # 仅一份语言布局
│   │   └── page.tsx              # 仅一份首页
│   ├── sitemap.ts
│   └── robots.ts
├── i18n/
│   ├── routing.ts               # 唯一受支持语言列表与路由策略
│   ├── request.ts               # 请求期加载翻译
│   ├── navigation.ts            # locale-aware 导航
│   ├── negotiation.ts           # 纯函数：根路径语言判断
│   └── preferences.ts           # 主动选择语言的 Cookie 读写规则
├── messages/
│   ├── zh.json
│   ├── en.json
│   └── ja.json
├── components/
│   └── LanguageSwitcher.tsx
└── proxy.ts                     # 根路径协商 + next-intl 路由集成
```

以上是**目标逻辑结构**，不是逐文件可直接复制的实现清单。`proxy.ts` 如何与 next-intl middleware 组合、根布局的实际放置方式、静态生成参数与错误页位置，应以选定版本的官方示例和 P1 构建验证为准。

`/zh`、`/en`、`/ja` 都映射到同一个 `app/[locale]/page.tsx`。新增 `/about` 只需新增一个 `app/[locale]/about/page.tsx`；新增法语主要新增 `fr.json` 并更新语言注册、SEO、测试和必要的本地化资源。构建生成不同语言的 HTML 是构建产物，不是维护三套源代码。

### 2.2 方案比较

| 方案 | URL 示例 | 共用一套页面 | 多语言搜索可发现性 | 主要代价 |
| --- | --- | --- | --- | --- |
| **A. 全语言前缀（推荐）** | `/en`、`/zh`、`/ja` | 是 | 清晰，适合 hreflang | 切换语言会进行路由导航 |
| B. 默认语言无前缀 | `/`（英文）、`/zh`、`/ja` | 是 | 可以 | 根路径的自动语言协商与英文规范地址需精心协调 |
| C. 查询参数 | `/?hl=ja` | 是 | 可以设计，但不作为优先方案 | 需自行确保 URL、canonical、hreflang、缓存与导航一致 |
| D. 无前缀、按 Cookie | `/` | 是 | 难以为每种语言提供独立规范 URL | 分享链接不固定语言，搜索可发现性受限 |

**决定依据**：公开品牌主页需要稳定、可分享、可索引的语言 URL；A 的页面维护量并不高于 B/C/D。Google 自家某些产品采用 `?hl=` 并不意味着所有网站都应复制其 URL 方案。此处选择是基于 saberu.com 的公开站点目标，而不是宣称查询参数技术不可行。

**未来改造提示**：从前缀改成无前缀不只是 `localePrefix` 一行；可能涉及文件路由、链接、Cookie、Proxy、缓存、SEO、历史 URL 重定向与测试。现在不预先承诺低成本迁移。

## 3. 语言识别、偏好与 Cookie

### 3.1 路由优先级

1. 请求路径已经带**受支持**的语言前缀时，该 URL 决定本次页面语言；不依据访问者地区覆盖它。
2. 仅当访问根路径 `/` 时，按以下顺序选择目标语言：
   - 用户**主动选择**并保存的语言偏好；
   - 浏览器 `Accept-Language` 中可匹配的受支持语言；
   - 可用且可信的 `CF-IPCountry` 地区兜底；
   - 默认 `en`。
3. 未支持的语言前缀不得悄悄映射到错误的内容；应按明确的 404/规范化策略处理并测试。

地区映射（**待确认的产品配置**）：`CN/SG/TW/HK/MO → zh`、`JP → ja`，其他不匹配则 `en`；`XX`、`T1` 等未知标记忽略。注意当前 `zh` 仅代表简体中文文案，繁体中文市场是否要分开，应在 P2 或后续扩展时决定。地区推断优先级低于浏览器语言，不把 IP 当作准确的语言偏好。

### 3.2 主动选择与“仅访问链接”必须区分

**产品要求**：用户主动点选“日本語”时，持久化偏好（建议 1 年）；用户只是打开朋友分享的 `/ja` 时，页面显示日语，但**不得因此覆盖原先主动选定的中文偏好**。随后访问 `/` 仍按主动选择的中文跳转。

next-intl 的默认 `NEXT_LOCALE` Cookie 会受语言路由协商影响，不能未经验证就认为“只有手动切换才写 Cookie”。因此 P1 推荐将“主动偏好”与库的内部协商 Cookie 解耦：

- 使用独立的偏好 Cookie（例如 `SABERU_LOCALE`，仅保存受支持的语言值），由语言切换动作显式写入；属性 `Path=/`、`SameSite=Lax`、生产 HTTPS 下 `Secure`、约 365 天有效期。
- 根路径 `/` 的自定义协商优先读取该 Cookie；next-intl 的 `localeCookie` 建议关闭或在 P1 明确验证并隔离其行为，避免 `NEXT_LOCALE` 覆盖用户主动偏好。
- Cookie 是用户偏好，不是身份认证；无须存储敏感信息。JavaScript 禁用时普通语言链接仍可访问相应语言，但不保证记录“主动偏好”，除非另做无 JS 的显式选择端点。

**验收用例**：主动选择 `zh` → 打开 `/ja` → 再访问 `/`，应返回 `/zh`。新访客日文浏览器访问 `/` 应进入 `/ja`；手动访问 `/en` 应保持英文且不强制跳走。

## 4. 语言切换、Session 与页面状态

使用 next-intl 的 locale-aware Link/Router 在相同业务路径之间导航，例如 `/zh/about → /ja/about`；通常属于客户端路由导航，不是传统浏览器整页重载，**但可能发出新的路由数据请求**，并且随路由段变化的组件**可能重新挂载**。

| 状态 | 本期承诺 / 后续设计原则 |
| --- | --- |
| 语言 URL | 更新为目标语言；优先 `replace`，避免返回键在两种语言间来回跳 |
| 当前业务路径 | 仍在同一业务页面；若目标语言没有对应页面，必须有明确回退策略 |
| 查询参数 | 语言切换不得无故丢失与业务相关的查询参数 |
| 滚动位置 | 产品目标是保持；需在实际浏览器测试 `scroll` 行为，不能只写“默认保持” |
| 登录 Session | 将来应由正确配置的 Cookie/服务端会话保持；当前项目尚无登录 |
| `useState`、Context、表单草稿 | **不保证天然保留**；未来交互页面需在稳定 Provider、Store 或持久化层中明确设计 |
| 上传、WebSocket、编辑器 | 本期无此功能；未来不得假设切换语言无副作用 |

**P1 只验证现有首页**：语言切换后 URL、内容、滚动与历史行为符合预期；可以增加一个仅用于测试的临时状态探针验证生命周期，但不要为了尚不存在的 Dashboard 引入全局状态库。未来新增复杂交互功能时再评估无前缀工作区或状态持久化。

## 5. SEO 与内容本地化

- 每个公开语言页面拥有唯一固定 URL、正确的 `<html lang>`、本语言标题/描述、指向**自身语言版本**的 canonical。
- `hreflang` 建立互相对应的语言版本关系；`x-default` 指向 `/` 语言入口。通过 Next.js Metadata API、next-intl 及 sitemap 组合实现时，避免重复或互相冲突的 alternate 声明。
- `sitemap.ts` 从同一份公开页面清单与语言注册表生成各语言 URL 和 alternates；仅纳入可索引的公开页面。`robots.ts` 允许抓取公开页面。
- `/` 是语言协商入口，优先采用临时重定向；避免把它作为某种语言的重复内容页。Googlebot 不保证始终来自美国或总进入英文；搜索引擎也**不保证**全部语言都被收录。
- 语言版本要有实际可读的翻译，避免只替换导航而主体仍是另一种语言。新增语言需校验缺失键、HTML lang、日期/数字、字体和布局。

## 6. 缓存与安全边界

| 请求类型 | 规则 |
| --- | --- |
| `/` | 按 Cookie、`Accept-Language`、地区动态决定临时跳转；明确 `Cache-Control: private, no-store`，Cloudflare 不得将某个用户的 Location 缓存给所有用户 |
| `/zh` `/en` `/ja` 等公开页 | 内容仅由路径及公开构建数据决定时可预渲染/缓存；避免在缓存页面中注入个性化内容 |
| `/sitemap.xml`、`/robots.txt` | 可按内容更新策略缓存 |
| 带登录或用户数据的未来路由 | 不得沿用公开页面的共享缓存规则 |

只接受已注册语言值；对 Cookie、路径与转发头做合法性检查，重定向目标只允许站内已知路径，避免开放重定向。`CF-IPCountry` 仅在可信的 Cloudflare → Tunnel 路径下用于兜底，不能无条件信任来自任意客户端的同名头。

## 7. 内部架构与技术选型

**请求路径**：浏览器 → Cloudflare → Tunnel → web 容器中的 Next.js。Tunnel 由主机主动建立连接；原则上无需为主页向公网开放应用入站端口。

| 方面 | 选型 / 验证要求 |
| --- | --- |
| Web 框架 | Next.js 16 App Router、TypeScript strict；以实施时验证通过的最新安全稳定补丁版本为准 |
| 国际化 | next-intl 4.x；`localePrefix: 'always'`；P1 验证所选精确版本与 Next.js 的兼容性 |
| 语言配置 | `i18n/routing.ts` 为语言列表唯一来源；`negotiation.ts` 是可单测的纯函数；偏好 Cookie 逻辑独立 |
| Proxy | Next.js 16 的 `proxy.ts`；将根路径自定义协商与 next-intl 的 Proxy 组合，避免两个规则互相覆盖 |
| 渲染 | 优先预渲染三个公开首页；实际构建验证 `generateStaticParams`、`setRequestLocale`、动态 API 与 Cache Components 的组合，不提前承诺一定静态 |
| 样式 | Tailwind CSS v4、集中设计 token、跟随系统深色模式；若未来提供手动主题切换再增加持久化逻辑 |
| 字体 | 拉丁文 Geist；中日文先采用合适系统字体，验证不同设备的排版 |
| 测试 | Vitest（纯函数/翻译一致性）+ Playwright（真实路由/切换/SEO/缓存） |
| 规范 | ESLint、Prettier、npm；以实际锁定版本的兼容结果决定具体版本，不固定未验证的兼容性断言 |
| 运行 | 多阶段 Dockerfile、Next standalone、非 root、最小权限；只读根文件系统须经构建和运行验证，必要的可写目录单独处理 |

**避免过度配置**：不要为了现在的一页主页预先引入登录、数据库、复杂全局 Store、CMS 或多套运行环境。

## 8. 构建、上线与回滚

1. **P1 本地框架**：在 `projects/homepage` 范围内创建工程、三语占位、语言协商、偏好持久化、SEO 元数据、测试与容器；不擅自提交 Git、不部署。
2. **P2 内容与设计**：补充品牌定位、介绍、服务/产品、联系邮箱、外链、favicon、OG 图；三语内容人工校对并测试移动端排版。
3. **P3 上线**：先构建并启动新容器，在不影响当前对外服务的条件下验证健康检查、路由、TLS/Host、响应头、缓存和 SEO；准备旧镜像、DNS 与维护页回退路径。**只有新源站验证通过后**才切换主域流量、调整/移除 Worker 维护页拦截，配置 `www` 规范跳转并复测。若切换失败，按已演练的步骤恢复旧流量。

> 当前文档不能证明现有 Worker、DNS、Tunnel 的真实配置；P3 必须在执行前核对 Cloudflare 实际规则，不能仅根据此草案假设“Worker 一定抢在源站前”。

### 8.1 P1 最小验收矩阵

| 类别 | 验收要求 |
| --- | --- |
| 路由 | `/zh`、`/en`、`/ja` 正确；不支持的 locale 行为确定；`/` 按规则临时跳转 |
| 语言优先级 | URL > 主动偏好（仅 `/`）> 浏览器 > 可信国家 > 英文；含冲突案例 |
| 偏好 | 主动选中文后访问 `/ja`，再访问 `/` 仍回 `/zh`；Cookie 有效期/安全属性正确 |
| 切换 | 站内导航；URL、文字、同路径、查询参数、滚动和浏览器返回行为符合定义 |
| 单代码源 | 三种语言共用同一份 `page.tsx`，不生成三套手工维护页面 |
| 翻译 | JSON 键一致、缺失键失败、语言切换器来源于统一注册表 |
| SEO | canonical、hreflang、`x-default`、sitemap、robots、HTML lang 互相一致 |
| 缓存 | `/` 不被 CDN 共享缓存；公开语言页无用户特定内容；验证关键响应头 |
| 兼容 | 锁定 Next.js/next-intl 版本，生产构建成功；预渲染结果与预期一致 |
| 容器 | 启动、健康检查、非 root、只读根文件系统（如采用）均实测通过 |

## 9. 风险、待确认事项与决策记录

### 9.1 需项目负责人确认

1. 是否正式批准**公开页面全部带语言前缀**（当前为推荐方案，不视为已经授权）。
2. `TW/HK/MO/SG` 暂映射简体中文是否接受；如不接受，可暂时全部按浏览器语言/英文兜底，不阻塞基础架构。
3. 是否批准独立的 `SABERU_LOCALE` 作为“用户主动选择”偏好 Cookie（推荐）。
4. 是否接受“P1 只做首页状态与导航验证；复杂 Dashboard 状态管理延后”的范围界限。
5. GitHub 远程仓库和 CI 可在 P1 后决定；未经明确授权不创建或推送仓库。

### 9.2 决策记录

- **推荐**：语言前缀 + 统一页面 + JSON 资源；理由是公开站点的 URL 确定性、SEO 与缓存清晰。
- **纠正**：语言切换是导航，不保证 React 组件实例及局部状态保持。
- **纠正**：next-intl 默认语言 Cookie 行为不等于“只在手动选择时更新”；主动偏好应单独管理并测试。
- **纠正**：未来变更 URL 策略不只是改一行配置。
- **保留待验证**：Next.js/next-intl/Cache Components 组合、真实 Cloudflare Worker 规则、只读容器运行要求。
