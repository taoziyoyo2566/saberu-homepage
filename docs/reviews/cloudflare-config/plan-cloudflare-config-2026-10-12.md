# saberu.com Cloudflare 配置代码化：方案

Status: APPROVED（批准范围：2026-10-12 本地实施，即 Terraform 配置、文档与 CI 检查，并用只读令牌导入现有资源、生成变更计划；任何 `terraform apply` 及其他对 Cloudflare 的写操作逐次授权）

本文件是 Cloudflare 配置代码化工作流唯一的当前方案。主页上线（[主页方案](../homepage-foundation/plan-homepage-foundation-2026-10-11.md)第 7 节 P3）在 Cloudflare 侧的变更通过本工作流执行；Cloudflare 现状见[现状调查记录](investigation-cloudflare-current-state-2026-10-12.md)。

## 决定与范围

2026-10-12（Asia/Tokyo），用户提出：“我想实现，通过当前项目的配置，你来负责管理cloudflare那边的配置，需要什么样的token权限。是否能实现？”。编码助手答复可行，建议用 Terraform 与 Cloudflare 官方 provider，说明纳入与不纳入的范围、三类令牌及其权限、“生成变更计划 → 用户批准 → 只执行该计划”的流程，并建议先只做只读部分。用户随后告知已创建写令牌，并询问 R2 状态存储的做法与令牌存放位置；编码助手给出步骤，并说明将此理解为同意该方向。用户答复：“同意”。决定：

- 用 Terraform 管理 saberu.com 在 Cloudflare 上与主页有关的配置。配置放在本仓库，由编码助手编写、维护并生成变更计划。
- 本次批准：本地实施（配置、运行脚本、文档、CI 检查与依赖更新配置）；把现状调查写成记录，不写其他子域名称与维护页上的坐标；用只读令牌把现有资源导入 Terraform 状态并生成变更计划。
- 不在本次批准内：任何 `terraform apply` 或其他 Cloudflare 写操作；R2 存储桶由用户在控制台创建。每次 apply 前先提交受保护操作说明，批准对象是一份保存下来的变更计划文件，批准只覆盖这一份。

## 1. 目标

Cloudflare 上与主页有关的配置以仓库中的声明为准：变更可审阅、可复现，线上是否被手动改过可以随时检查，恢复时有明确的目标配置。编码助手负责维护这份配置并在每次变更前给出计划；用户保留每次执行的批准权。

## 2. 批准时的现状

- Cloudflare：主域全部请求由维护页 Worker 返回 503；`www` 没有 DNS 记录；根域另有邮件记录，区域内另有在用的子域。维护页 Worker 挂在路由上还是自定义域上，从外部无法判断。详见[现状调查记录](investigation-cloudflare-current-state-2026-10-12.md)。
- 本仓库没有 Cloudflare 配置代码；主机未安装 Terraform。
- 令牌：用户已在控制台创建写令牌，尚未保存到本机；只读令牌与 R2 存储桶尚未创建。

## 3. 设计

### 管理范围

| 由本仓库配置管理 | 不纳入（Terraform 不读写其配置） |
|---|---|
| 主页专用 Tunnel 及其转发规则 | 根域的邮件记录（MX、SPF、DMARC）与各类验证 TXT 记录 |
| `saberu.com` 与 `www` 的 DNS 记录 | 区域内其他子域及其服务 |
| `www` 到主域的 301 跳转规则 | 账户中其他 Tunnel 与 Worker |
| 维护页 Worker 的挂载（导入后在 P3 移除） | 域名注册、DNSSEC、区域本身 |
| 以后按需加入，如缓存规则 | HSTS 等对整个区域生效的设置，纳入前另行决定 |

Terraform 只管理配置中声明或导入的资源，未声明的记录与设置不受影响。令牌无法把权限限制到单条 DNS 记录，所以范围的执行保障是变更计划审阅：计划中出现上表右列的任何对象，即停止，不执行。

### 运行方式

- Terraform CLI 以官方容器镜像运行，镜像写成“标签 + 摘要”，不在主机安装。`cloudflare/cloudflare` provider 用 `~>` 限定主版本，`.terraform.lock.hcl` 提交到仓库，与项目“范围 + 锁文件”的依赖约定一致；provider 由 Dependabot 更新。
- 状态存放在 R2（Terraform 的 S3 兼容后端），存储桶只用于本状态。状态含 Tunnel 连接令牌，不进入仓库。账户 ID、区域 ID 与存储桶名等标识不写进公开仓库，运行时从被 Git 忽略的文件传入。
- 凭据只放在 `deploy/*.env`（被 Git 与镜像构建排除，权限 600）：只读令牌、写令牌、R2 凭据各一个文件。日常导入与生成计划只加载只读令牌；写令牌只在执行已批准的计划时加载。
- CI 只做格式检查与配置校验，不使用任何令牌，不连接后端。

### 变更流程

1. 修改仓库中的配置。
2. 用只读令牌生成变更计划，并保存为计划文件。
3. 向用户提交受保护操作说明与计划摘要（新增、修改、删除了哪些资源）。
4. 用户批准后，用写令牌执行这一份计划文件；配置或线上状态在批准后有变化时，重新生成计划并重新请求批准。
5. 外部验证结果，并按主页方案与工作区规则记录。

### 与主页 P3 的关系

P3 在 Cloudflare 侧的变更（建 Tunnel、切换 DNS、`www` 跳转、移除维护页挂载）通过本工作流的配置与流程执行。P3 的进入条件、检查点与恢复目标仍以主页方案为准。移除维护页挂载之前，备份其 Worker 代码与挂载方式作为恢复资料；备份含维护页内容，不进入公开仓库。

## 4. 阶段与验收

**阶段 A：本地框架与导入（已批准）**

- 交付：Terraform 配置（provider、后端、变量、对现有资源的导入）、运行脚本、开发文档中的使用说明与停止条件、CI 检查、Dependabot 配置。
- 进入条件：用户保存只读令牌与 R2 凭据并建好存储桶。不依赖令牌的部分可以先做。
- 验收：
  - `terraform fmt -check` 与 `terraform validate` 在本地和 CI 中通过；
  - 状态保存在 R2；
  - 导入现有资源后，用只读令牌生成的变更计划显示无变更，证明配置与线上一致；
  - 仓库中没有凭据、账户 ID 或区域 ID；
  - 现状调查记录补全令牌可见的事实（维护页挂载方式、主页相关 DNS 记录、已有 Tunnel、相关区域设置）。

**阶段 B：P3 中的线上变更（逐次授权）**

- 交付：主页 Tunnel 与转发规则、DNS 切换、`www` 跳转、移除维护页挂载。
- 进入条件：主页方案 P3 的进入条件全部满足，并为写令牌设定有效期与来源 IP 限制。
- 验收：以主页方案 P3 的发布检查点为准；执行后用只读令牌再次生成计划，显示无变更。

## 5. 风险与限制

- **权限粒度**：DNS Edit 作用于整个区域。Cloudflare Tunnel Edit 与 Workers Scripts Edit 是账户级权限，能触及账户内所有 Tunnel 与 Worker。缓解：
  - 执行前审阅计划；
  - 写令牌只在执行时加载；
  - 维护页若为自定义域，移除这一步由用户在控制台完成，或使用一次性的临时令牌，不长期持有 Workers Scripts Edit。
- **状态含机密**：R2 凭据只授予该存储桶的对象读写；R2 是否支持 Terraform 的状态锁，在阶段 A 实测，单人使用时影响有限。
- **不常驻**：编码助手只在会话中工作。检查线上是否被手动改过需要手动生成计划；CI 定时检查以后另行决定。
- **写令牌已提前创建**：在阶段 B 之前保持不加载；建议尽早设有效期与来源 IP 限制。
